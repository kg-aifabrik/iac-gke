# Day-2 operations — capability assessment

- **Status:** Draft assessment (iterating before it becomes an implementation plan)
- **Date:** 2026-07-01
- **Scope:** what it takes to run Day-2 operations against a factory-built cluster (`dev-fop` today) — enumerated per subsystem and classified *supported / partial / needs-building*, with a ranked build backlog. Produced from a codebase audit; treat the classifications as the starting point for discussion.
- **Related:** [ADR-0009](../adr/0009-cluster-purpose-expansion.md) (the factory model), [cluster-build.md](../implementation/cluster-build.md), [runbook 02](../runbooks/02-cluster-bringup.md).

## The model (how a Day-2 change flows)

Every change is the same gated, config-driven path as the build: **edit `config/clusters.yaml` → `bootstrap/add-cluster-purpose.sh` regenerates the root → PR (`terraform-plan` posts the plan) → gated `terraform-apply` → SRE approves**. The plan preview is the blast-radius check (in-place vs replace vs destroy).

## Core finding

The cluster factory has a clean registry -> generator -> cluster-stack -> module pipeline plus a well-built verifier and drift guard, but Day-2 readiness is uneven. Only a narrow set of operations is genuinely smooth end-to-end (autoscaling min/max resize, release channel, maintenance window, deletion protection, Cloud NAT, ingress hostname add/remove, cert rotation, SRE operator management, Connect Gateway access). The dominant failure mode is a config-surface gap, not a module gap: the module + cluster-stack already support ~24 additional inputs (spot, disk size, backup schedule/retention/enable, confidential pool, autoscaling_profile, node_locations, min TLS, app/proxy repo ids, cluster_role, all four network CIDRs) but render._render_main never emits them, so they are frozen at defaults and un-tunable without editing generator code. A second tier is genuinely unbuilt at the module layer (arbitrary/GPU node pools, upgrade surge tuning, control-plane/node version pinning, maintenance exclusions, security posture, Cloud Armor attachment, extra Artifact Registry repos + cleanup policies, Binary Authorization enforce, app Workload Identity, storage class customization, VPC firewall, namespace-scoped RBAC). The most acute operational risks are cross-cutting meta-gaps: the drift guard exists but is not wired into CI (a config-only PR previews nothing and merges undetected, and cluster-build.md:310 falsely claims CI runs it), there is no documented modify-an-existing-cluster runbook, no post-apply verification loop, no rollback story, and no plan-time warning distinguishing in-place from replace/immutable changes.

In short: the dominant issue is a **config-surface gap** (the generator emits ~20 of ~44 module inputs), compounded by a few **cross-cutting operational gaps** (no CI drift guard, no plan preview for config-only PRs, no modify-cluster runbook, no rollback, no replace-warning). The first fixes are cheap and high-value.
